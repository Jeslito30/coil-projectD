# Data and MQTT Topic Design — Project D

**Version:** 0.2 · **Status:** Proposal — awaiting Philippines pair review · **Updated:** 2026-11-04  
**Owner:** Joint (PL draft) · **Reviewer:** Philippines pair (approval required before implementation)  
**Applies to:** Both simulators, Mosquitto ACLs, Telegraf ingestion, Grafana queries/alerts and test analysis

Both cities MUST implement this contract identically. A change to IDs, topics, field types, timestamps, alert semantics or ACLs requires a pull request reviewed by the other pair and a compatibility check of all dependent components.

---

## 1. Sensors

### 1.1 Sensor ID format

```text
<CITY>-<TYPE>-<NN>
```

| Part | Allowed values | Rule |
| --- | --- | --- |
| `CITY` | `MATI`, `SZCZ` | Upper case, exactly four letters |
| `TYPE` | `TEMP`, `HUM`, `AIR` | Upper case |
| `NN` | `01`–`99` | Two digits, zero-padded |

The sensor ID is also its **MQTT username** and **MQTT client ID**. Client IDs must be unique among concurrently connected clients: a second connection with the same ID can disconnect the first. Never run two active publishers using the same sensor identity.

The username/client ID is an identifier, not a secret. Each identity still requires its own strong password stored outside Git.

### 1.2 Initial sensor set

| City | JSON `city` | Topic city | `sensor_type` | Sensor ID |
| --- | --- | --- | --- | --- |
| Mati | `Mati` | `mati` | `temperature` | `MATI-TEMP-01` |
| Mati | `Mati` | `mati` | `humidity` | `MATI-HUM-01` |
| Mati | `Mati` | `mati` | `airquality` | `MATI-AIR-01` |
| Szczecin | `Szczecin` | `szczecin` | `temperature` | `SZCZ-TEMP-01` |
| Szczecin | `Szczecin` | `szczecin` | `humidity` | `SZCZ-HUM-01` |
| Szczecin | `Szczecin` | `szczecin` | `airquality` | `SZCZ-AIR-01` |

### 1.3 Sensor types and units

| `sensor_type` | Quantity | JSON `unit` | Display precision |
| --- | --- | --- | --- |
| `temperature` | Air temperature | `C` | 1 decimal place |
| `humidity` | Relative humidity | `%RH` | 1 decimal place |
| `airquality` | PM2.5 concentration | `ug/m3` | 1 decimal place |

Air quality is modelled as PM2.5 so the value has a physical unit rather than an unspecified AQI scale. Units use plain ASCII in payloads. `unit` is fixed for a sensor type and MUST agree with this table.

## 2. MQTT topics

### 2.1 Reading topics

```text
coil/<city>/<sensor_type>/<sensor_id>
```

- `<city>` is `mati` or `szczecin` in lower case.
- `<sensor_type>` is `temperature`, `humidity` or `airquality`.
- `<sensor_id>` exactly matches section 1.1 and the payload's `sensor_id`.

Canonical topics:

```text
coil/mati/temperature/MATI-TEMP-01
coil/mati/humidity/MATI-HUM-01
coil/mati/airquality/MATI-AIR-01
coil/szczecin/temperature/SZCZ-TEMP-01
coil/szczecin/humidity/SZCZ-HUM-01
coil/szczecin/airquality/SZCZ-AIR-01
```

### 2.2 Status topics

```text
coil/<city>/status/<sensor_id>
```

| Event | UTF-8 payload | Retained | QoS |
| --- | --- | --- | --- |
| Client connects and is ready | `online` | Yes | 1 |
| Client disconnects cleanly | `offline` | Yes | 1 |
| Connection drops and broker publishes Last Will | `offline` | Yes | 1 |

Status indicates MQTT connection state only. It does **not** replace the missing-reading alert: a process can remain connected while its publishing loop is stopped. Status payloads are plain text and are not sent through the JSON reading parser.

### 2.3 Reserved topics — optional Phase 7 only

```text
coil/<city>/computer/<host_id>/metrics
coil/<city>/wol/<relay_id>/cmd
coil/<city>/wol/<relay_id>/result
```

These names are reserved to prevent collisions. Their schemas and dedicated least-privilege ACLs must be approved before the extension is implemented; the core sensor ACLs do not grant access to them.

## 3. JSON reading contract

### 3.1 Fields

Every reading is one UTF-8 JSON object. Unknown fields MUST NOT be required for v1 consumers; producers MUST NOT add fields that change existing meanings without increasing `schema_version`.

| Field | JSON type | Required | Validation rule |
| --- | --- | --- | --- |
| `schema_version` | integer | Yes | Exactly `1` |
| `sensor_id` | string | Yes | Valid ID and exact match with the topic's final segment |
| `city` | string | Yes | `Mati` or `Szczecin`; must agree with the topic city |
| `sensor_type` | string | Yes | Valid type and exact match with the topic's third segment |
| `timestamp_utc` | string | Yes | ISO 8601 UTC with exactly three fractional digits and `Z`, for example `2026-11-10T08:30:00.123Z` |
| `seq` | integer | Yes | Starts at `0` for a simulator run and increases by exactly `1` for each reading generated by that sensor in that run |
| `value` | number | Yes | Finite number; producers serialise with a decimal point (for example `21.0`) and ingestion explicitly converts to float |
| `unit` | string | Yes | Exact unit for `sensor_type` from section 1.3 |
| `simulated` | boolean | Yes | Exactly `true` |

The formal validator in `simulators/common/schema.json` should enforce the field set, types, patterns and `additionalProperties` policy chosen by the team. Cross-field checks — topic agreement, allowed city/type/unit combinations and finite values — must also be implemented because a basic JSON Schema alone may not express every relationship.

JSON itself has one numeric type. The decimal-point convention avoids parser-dependent integer inference, while Telegraf's explicit `type = "float"` is the ingestion safeguard. Conflicting numeric field types can cause InfluxDB write failures or conflicts; do not rely on whichever value happens to arrive first.

### 3.2 Canonical examples

```json
{"schema_version":1,"sensor_id":"SZCZ-TEMP-01","city":"Szczecin","sensor_type":"temperature","timestamp_utc":"2026-11-10T08:30:00.123Z","seq":42,"value":6.4,"unit":"C","simulated":true}
```

```json
{"schema_version":1,"sensor_id":"MATI-HUM-01","city":"Mati","sensor_type":"humidity","timestamp_utc":"2026-11-10T08:30:00.481Z","seq":42,"value":81.7,"unit":"%RH","simulated":true}
```

```json
{"schema_version":1,"sensor_id":"SZCZ-AIR-01","city":"Szczecin","sensor_type":"airquality","timestamp_utc":"2026-11-10T08:30:00.902Z","seq":42,"value":18.3,"unit":"ug/m3","simulated":true}
```

### 3.3 Why these rules exist

| Rule | Reason |
| --- | --- |
| Millisecond UTC timestamps | Second precision cannot describe delays expected in tens to hundreds of milliseconds |
| Timestamp at reading creation | Supports end-to-end delay and offline-queue analysis |
| Per-run `seq` | Detects gaps and repeated sequence values within a controlled test run |
| Explicit float conversion | Prevents numeric type inconsistency at ingestion |
| `schema_version` | Makes future contract migration explicit |
| `simulated: true` | Prevents synthetic readings being mistaken for physical measurements |

`seq` resets when a simulator run starts. Interruption analysis MUST therefore record process starts/restarts and compare sequence values within a single run unless persistent sequence state is deliberately added later. A reset to `0` must not be misclassified as a duplicate or message loss.

## 4. Publishing and reconnect behaviour

### 4.1 Core settings

| Setting | Required value | Reason / constraint |
| --- | --- | --- |
| Nominal interval | 30 s per sensor | Project requirement; test override is allowed |
| Reading QoS | 1 | At-least-once delivery; duplicates remain possible |
| Reading retain | `false` | Prevents an old retained reading making a stopped sensor look current |
| Status retain | `true` | New subscribers can discover the latest connection state |
| MQTT clients | One per sensor | Supports per-sensor identity, client ID, Last Will and ACL |
| MQTT protocol | MQTT 3.1.1 for the baseline | Use clean session `false`; an MQTT 5 implementation must explicitly configure equivalent persistent-session semantics |
| Offline behaviour | Bounded, ordered queue; flush after reconnect | Supports interruption tests without claiming unlimited or lossless buffering |
| Broker endpoint | `10.66.0.1:8883` through WireGuard | See `vpn-plan.md` |
| TLS validation | Trust the project CA, verify the certificate for `10.66.0.1`, do not disable verification | Prevents encrypted but unauthenticated server connections |
| TLS version | TLS 1.2 or newer | Baseline transport security |

### 4.2 Offline queue and restart requirements

The implementation MUST document and test its queue limit, storage location, persistence across process restarts, ordering and overflow policy. A memory-only queue is acceptable only if that limitation is explicit in the interruption report.

- Queue readings per sensor and preserve generation order during normal draining.
- Record queue capacity, current utilisation and every overflow/drop event in the local test log.
- On reconnect, do not mark the sensor healthy solely because the socket connected; verify that publishing has resumed.
- Separate readings generated during an outage from normal-operation readings in delay analysis.
- Do not claim “no data loss” unless sequence evidence and queue logs cover the complete test window, including process restarts.

### 4.3 QoS 1, duplicates and InfluxDB

QoS 1 can deliver the same publication more than once. In InfluxDB, a point with the same measurement, tag set and timestamp overwrites fields on the same point, so a retransmitted reading with unchanged `timestamp_utc` may collapse into one stored point.

That collapse is **not** proof that no duplicate occurred, and the stored `seq` value does not count duplicates. Duplicate analysis is recommended, not a mandatory Project D test. If performed, it SHOULD use evidence captured before that overwrite, such as a timestamped raw subscriber log, broker trace or client acknowledgement log; stored point counts alone must not be presented as duplicate evidence. Sequence gaps in stored data likewise need restart and queue-overflow logs before they can be attributed to VPN loss.

### 4.4 Required simulator options

| Option | Required behaviour |
| --- | --- |
| `--config <file>` | Load broker, port, CA path and sensor list. Real configuration and passwords stay outside Git; commit only examples |
| `--anomaly <sensor_id>` | Generate a reading outside that sensor's alert threshold for Alert 1 testing |
| `--silence <sensor_id>` | Stop readings for that sensor while keeping its MQTT connection alive for Alert 2 testing |
| `--interval <seconds>` | Override 30 s only for testing; record the value in evidence |

Credentials should come from environment variables or a local ignored secret file. Configuration examples must not contain real passwords, private keys or tokens.

## 5. Simulated value ranges

Values follow a slow random walk inside the normal range. Consecutive changes must not exceed the maximum step except when the explicit `--anomaly` test mode is active.

| City | Sensor type | Normal range | Maximum normal step |
| --- | --- | --- | --- |
| Mati | temperature | 24.0–33.0 C | 0.3 |
| Mati | humidity | 65.0–95.0 %RH | 1.0 |
| Mati | airquality | 5.0–35.0 ug/m3 | 1.5 |
| Szczecin | temperature | -3.0–10.0 C | 0.3 |
| Szczecin | humidity | 70.0–98.0 %RH | 1.0 |
| Szczecin | airquality | 5.0–60.0 ug/m3 | 2.0 |

These are plausible synthetic values for November, not real observations. Anomaly-mode values are intentionally invalid or unusual and must not be included in normal-operation statistics.

## 6. Alert definitions

### 6.1 Alert 1 — reading outside threshold

Evaluate the latest reading **per sensor series**, not one global latest value:

| City | Sensor type | Alert if below | Alert if above |
| --- | --- | --- | --- |
| Mati | temperature | 20.0 C | 38.0 C |
| Mati | humidity | 40.0 %RH | 100.0 %RH |
| Mati | airquality | — | 55.5 ug/m3 |
| Szczecin | temperature | -15.0 C | 20.0 C |
| Szczecin | humidity | 40.0 %RH | 100.0 %RH |
| Szczecin | airquality | — | 75.0 ug/m3 |

The normal random-walk ranges do not cross these thresholds. Every `--anomaly` target must produce a value that crosses the relevant boundary. A threshold crossing and its recovery should both be visible in alert history.

### 6.2 Alert 2 — sensor stops sending

- A sensor is silent when the newest stored reading for its series is older than **120 s** (four nominal intervals).
- Grafana evaluates the condition every **30 s**. With immediate evaluation after the threshold, expected detection is approximately **120–150 s**, plus ingestion or evaluation delay; no additional 120 s pending period should be added.
- The alert recovers when a fresh reading arrives and the condition is false at evaluation.
- `--silence` keeps MQTT connected so the test proves that the missing-reading condition works independently of Last Will status.
- If `--interval` is changed for a test, either retain and report the production 120 s threshold or adjust it explicitly in a separate test configuration; never compare unreported thresholds.

No-data behaviour must be configured deliberately. A query returning no rows should not silently disable alerting or make every sensor appear healthy.

## 7. Ingestion and delay measurement

### 7.1 InfluxDB layout

| InfluxDB element | Source / type |
| --- | --- |
| Measurement | `environment` |
| Tags | `sensor_id`, `city`, `sensor_type` |
| Fields | `value` float, `seq` integer, `delay_ms` float added by Telegraf |
| Point timestamp | Parsed `timestamp_utc` |
| Excluded from this layout | `unit`, `simulated` and `schema_version` remain validated payload metadata; add them only through a reviewed schema change |
| Retention | Set by the approved InfluxDB initialisation/deployment configuration and recorded in the setup guide |

### 7.2 Telegraf input and processor baseline

Validate the exact plugin options against the Telegraf version pinned by the deployment. The intended configuration is:

```toml
[[inputs.mqtt_consumer]]
  servers = ["ssl://mosquitto:8883"]
  topics = [
    "coil/+/temperature/+",
    "coil/+/humidity/+",
    "coil/+/airquality/+",
  ]
  qos = 1
  client_id = "telegraf-ingest"
  persistent_session = true
  username = "telegraf"
  password = "${MQTT_TELEGRAF_PASSWORD}"
  tls_ca = "/etc/telegraf/certs/ca.crt"
  insecure_skip_verify = false
  data_format = "json_v2"

  [[inputs.mqtt_consumer.json_v2]]
    measurement_name = "environment"
    timestamp_path = "timestamp_utc"
    timestamp_format = "2006-01-02T15:04:05.000Z07:00"

    [[inputs.mqtt_consumer.json_v2.tag]]
      path = "sensor_id"
    [[inputs.mqtt_consumer.json_v2.tag]]
      path = "city"
    [[inputs.mqtt_consumer.json_v2.tag]]
      path = "sensor_type"

    [[inputs.mqtt_consumer.json_v2.field]]
      path = "value"
      type = "float"
    [[inputs.mqtt_consumer.json_v2.field]]
      path = "seq"
      type = "int"

# Processing time minus reading creation time, in milliseconds.
[[processors.starlark]]
  namepass = ["environment"]
  source = '''
load("time.star", "time")

def apply(metric):
    metric.fields["delay_ms"] = (time.now().unix_nano - metric.time) / 1000000.0
    return metric
'''
```

Telegraf's Mosquitto username must be authorised to read exactly the reading topics. Status topics are deliberately excluded because their payload is plain text. The server certificate used by Mosquitto must be valid for the name Telegraf uses to connect; if certificate validation expects `10.66.0.1` but Telegraf connects to `mosquitto`, either include both identities in the certificate SANs or use a validated internal name consistently. Never solve a name mismatch by enabling `insecure_skip_verify`.

### 7.3 Meaning and limitations of `delay_ms`

```text
delay_ms = Telegraf Starlark processing time (server clock)
           − timestamp_utc (simulator clock)
```

This is an **end-to-end ingestion delay approximation**, not a pure network round-trip time. It includes network travel and can include broker queueing, Telegraf scheduling and processing. The processor runs after message receipt, so the report must not describe it as an exact broker-arrival timestamp.

Before each test:

1. Record `chronyc tracking` on the server and each simulator host, plus drift checks where required by `vpn-plan.md`.
2. Record simulator start/restart times, interval, firmware/software revision, queue policy and test start/end.
3. Preserve sequence, restart and queue-overflow observations needed for gap analysis. Raw subscriber/broker logs are recommended for optional duplicate analysis, not required for the baseline.
4. Report count, mean, median, p95, maximum and minimum by city and sensor where practical. Include clock uncertainty and negative values rather than hiding them.
5. Report normal connected operation separately from messages generated during an outage and drained later. Queued messages can legitimately have very large `delay_ms` values.

## 8. MQTT ACL baseline

Usernames equal sensor IDs. Every sensor can write only its own reading and status topics. Telegraf and `test-observer` can read only reading topics; the dashboard identity can read only status topics.

```text
# Szczecin sensors
user SZCZ-TEMP-01
topic write coil/szczecin/temperature/SZCZ-TEMP-01
topic write coil/szczecin/status/SZCZ-TEMP-01

user SZCZ-HUM-01
topic write coil/szczecin/humidity/SZCZ-HUM-01
topic write coil/szczecin/status/SZCZ-HUM-01

user SZCZ-AIR-01
topic write coil/szczecin/airquality/SZCZ-AIR-01
topic write coil/szczecin/status/SZCZ-AIR-01

# Mati sensors
user MATI-TEMP-01
topic write coil/mati/temperature/MATI-TEMP-01
topic write coil/mati/status/MATI-TEMP-01

user MATI-HUM-01
topic write coil/mati/humidity/MATI-HUM-01
topic write coil/mati/status/MATI-HUM-01

user MATI-AIR-01
topic write coil/mati/airquality/MATI-AIR-01
topic write coil/mati/status/MATI-AIR-01

# Ingestion
user telegraf
topic read coil/+/temperature/+
topic read coil/+/humidity/+
topic read coil/+/airquality/+

# Dashboard status panel
user dashboard
topic read coil/+/status/+

# Security-test observer (read-only; used only by tests/security/mqtt_security_test.py)
user test-observer
topic read coil/+/temperature/+
topic read coil/+/humidity/+
topic read coil/+/airquality/+
```

`test-observer` exists so the security test does not need Telegraf's production password on a laptop. Disable it (remove it from the password file) outside test windows if the team prefers.

Explicit per-user write rules are intentional. A broad pattern such as `pattern write coil/+/+/%u` could allow `SZCZ-TEMP-01` to publish to `coil/mati/humidity/SZCZ-TEMP-01`, violating the city/type/topic contract.

The ACL file does not replace payload validation. A sensor can still send a malformed value on its own valid topic. Schema validation and a malformed-payload rejection/error test are recommended, but they are not mandatory Project D deliverables with an assigned component. Phase 7 identities require separate, reviewed ACL entries and must not be added to these wildcard groups by default.

## 9. Verification matrix

Rows marked **Recommended** are optional improvements, not acceptance gates for the mandatory Project D baseline.

| Test | Expected result | Evidence |
| --- | --- | --- |
| Valid reading from every sensor | Accepted and stored with correct tags/types/timestamp | Payload, broker/client result, InfluxDB query |
| Wrong password | Connection/publish rejected | Dated client log and exit result |
| No credentials | Rejected | Dated client log and exit result |
| Plaintext port 1883 | Connection refused or otherwise fails because no listener exists | Client log plus listener inspection |
| TLS without trusted CA / wrong server identity | Rejected | Client TLS error; no insecure bypass enabled |
| Own-topic write | Accepted | Client log and stored point |
| Another sensor's topic write | Denied by ACL | Client/broker log showing denial |
| **Recommended:** valid topic with malformed payload | If validation is implemented, reject or explicitly record the invalid message without a silent field-type change | Validation behaviour and, when available, its error log |
| Anomaly | Correct per-sensor alert fires and recovers | Alert history and anomalous payload |
| Silence while connected | Missing-reading alert fires despite retained `online` status | Timeline with last reading and evaluation |
| VPN interruption | Reconnect and queue behaviour measured; gaps, restarts and overflow distinguished | Sequence analysis, restart/queue logs and clock offsets; duplicate analysis is recommended only when suitable raw logs exist |

## 10. Changes from the Check-in 1 draft (30 Oct)

| Check-in 1 draft | Current design | Reason |
| --- | --- | --- |
| One ID per city, but an example used a per-sensor ID | One ID per sensor | Removes contradiction and enables per-sensor credentials, ACLs and tests |
| Temperature, humidity, wind, UV and air quality | Temperature, humidity and PM2.5 | Covers the mandatory baseline; other types can be added through versioning |
| Topic segment `air` | `airquality` | Topic and payload use the same type value |
| Air quality as unspecified AQI | PM2.5 in `ug/m3` | Uses a physical quantity rather than an unspecified national index |
| Unit `°C` | `C` | ASCII payload convention |
| Seconds-only timestamp | Milliseconds with `Z` | Supports delay analysis |
| No sequence number | Per-run `seq` | Supports controlled gap analysis and optional duplicate analysis with restart logs |
| `simulated: true` | Retained | Clearly labels synthetic data |

### Clarifications introduced in v0.2

- Distinguished JSON's generic number type from explicit float conversion at ingestion.
- Defined per-run sequence semantics and required restart/queue-overflow evidence.
- Explained why InfluxDB overwriting cannot prove or count QoS 1 duplicates; raw-log duplicate analysis is recommended, not required.
- Made offline queues bounded and observable instead of implying unlimited delivery guarantees.
- Defined a 120–150 s nominal silence-detection window and required intentional no-data behaviour.
- Renamed delay as an end-to-end ingestion approximation and required clock-uncertainty reporting.
- Added TLS certificate-name guidance and required invalid-certificate tests; malformed-payload validation is recommended.
